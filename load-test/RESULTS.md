# Gateway 부하 테스트 결과 (스테이징 서버)

측정일: 장애 시나리오 2026-10-01(Node 22), **지연 측정 2026-10-06(Node 26 재측정)**. 저장소의 `engines`(`>=26`)와 맞추려고 지연을 다시 쟀고, 장애 시나리오는 다시 재지 않았습니다.

재현 방법과 해석 원칙은 [README.md](./README.md)에 있습니다. 이 문서는 한 번의 실측 결과와 그 한계입니다.

## 환경

| 항목 | 값 |
|---|---|
| 서버 | 스테이징 4 vCPU / 7.8GiB / x86_64 / Docker 29.1.3 |
| CPU 배치 | k6 = 코어 3, Gateway = 코어 1(Node 단일 스레드), 나머지 = 코어 0,2 |
| Eureka | 실제 Eureka 서버 이미지 `steeltoeoss/eurekaserver` (digest `sha256:35214871…`, Java 8 / Spring Boot 1.x). lease 90초(클라이언트 `nestjs-eureka` 등록값), eviction 60초, 응답 캐시 30초(설정으로 명시), self-preservation 끔 |
| self-preservation 확인 | lease 5초 더미 인스턴스를 등록하고 갱신을 멈추니 약 45초에 evict됨 → eviction이 막히지 않음 |
| Node.js | 지연 측정: `node:26-slim` (Gateway·백엔드 공통). 장애 시나리오: `node:22-slim` (재측정 안 함. Eureka lease·캐시 타이밍이 결과를 정하는 시나리오라 영향이 작을 것으로 보지만 확인하지는 않았습니다) |
| 백엔드 | `nestjs-eureka`를 쓰는 최소 NestJS 앱 3개, 응답 20ms + 최대 10ms 지터, 컨테이너 IP를 등록 |
| 부하 | k6 일정 도착률 **200 req/s**. 보정에서 Gateway(코어 1개)가 p95 < 100ms·누락 0·전부 200을 유지하는 최대 처리량은 약 400 req/s였고(800에서 실패), 그 50%로 측정 |

## 1. Gateway가 더하는 지연

Node 26, 워밍업 15초 후 60초 측정, 시나리오당 **5회 × 2가지 실행 순서**(직접→경유→공개 / 공개→경유→직접) = 10회, 중앙값. 요청은 전부 200, 누락 0.

| 시나리오 | p50 | p95 | p99 |
|---|---|---|---|
| 백엔드 직접 | 25.06 ms | 29.66 ms | 30.28 ms |
| Gateway 경유 (JWT 검증) | 26.96 ms | 31.80 ms | 38.08 ms |
| Gateway 경유 (공개 경로, JWT 없음) | 26.71 ms | 31.55 ms | 36.96 ms |

| 비교 | p50 | p95 | p99 |
|---|---|---|---|
| **Gateway 오버헤드** (경유 − 직접) | **+1.9 ms** | **+2.1 ms** | +7.8 ms |
| **JWT(RS256) 검증 비용** (경유 − 공개) | +0.3 ms | +0.3 ms | +1.1 ms |

읽는 법:

- **오버헤드는 p50·p95 모두 2ms 안팎**입니다. 순서별로 p50 1.96 / 1.93ms, p95 2.34 / 2.08ms였습니다. 리포트는 순서별 p95 오버헤드 차이(0.26ms)가 큰 값의 11%라 "노이즈"로 표시했지만 절대 차이는 0.3ms 이하입니다.
- 경유 p95는 10회 중 9회가 31.7~32.3ms이고 1회만 34.1ms로 튀었습니다.
- **JWT 검증은 사실상 무시할 수준**입니다 (p50·p95 +0.3ms). 공개 경로와 비교한 값이라 인증 외 차이는 없습니다.
- Gateway 자체 메트릭(경유, 보호 경로, 중앙값): 요청당 Eureka 조회 0.76ms, Gateway CPU 0.35 코어.

### Node 22와 비교 (같은 프로토콜, 5일 간격)

| 항목 | Node 22 (10/01) | Node 26 (10/06) |
|---|---|---|
| 오버헤드 p50 | +2.5 ms | +1.9 ms |
| 오버헤드 p95 | +4.5 ms (반복별 노이즈 큼) | +2.1 ms |
| 오버헤드 p99 | +33 ms | +7.8 ms |
| JWT 비용 p50 | +0.2 ms | +0.3 ms |

- 차이가 가장 큰 곳은 **p99 꼬리**입니다. Node 22에서는 이벤트 루프 지연(p99 40ms / 최대 104ms)과 크기가 맞아서 이벤트 루프 정지를 의심했지만 GC를 직접 측정하지는 않았습니다.
- **Node 버전이 꼬리를 줄였다고 단정하지 않습니다.** 바뀐 것은 Node 버전이지만 측정 시점도 5일 달라서 같은 호스트의 다른 요인을 배제하지 못했고, Node 26 쪽은 이벤트 루프 지연과 GC를 재측정하지 않았습니다.
- 두 측정 모두 Eureka 조회(Node 22에서 p99 6.9ms)로는 꼬리를 설명하지 못합니다.

## 2. 백엔드 장애 시나리오

이 절의 수치는 **Node 22(2026-10-01)** 에서 잰 것입니다.

백엔드 `svc-a` 하나만 장애를 주입하고 `svc-b/c`는 그대로 둡니다. 각 시나리오 3회, 200 req/s로 `svc-a`에 부하를 줍니다. 모든 시나리오에서 **Gateway의 Eureka 관련 경고(heartbeat/폴 실패)는 0건**이었습니다.

| 시나리오 | 무엇이 죽나 | Gateway가 UP=0을 보기까지 | 502 응답 | 비고 |
|---|---|---|---|---|
| SIGTERM | 프로세스 (정상 종료, 라이브러리가 등록 해제) | 16 / 21 / 28 초 | 1,491 / 2,389 / 3,871 | 즉시가 아님: Eureka 응답 캐시(30초)·폴(10초) 때문 |
| **SIGKILL** | 프로세스 (크래시/OOM, 호스트 생존) | **211 / 228 / 248 초** | **40,583 / 44,283 / 48,115** | UP이 1 이상인 채로 요청이 계속 실패 |
| 호스트 소실 | 컨테이너 전체 (서버 다운) | 201 / 221 / 245 초 | 1,701~1,962 + **요청 매달림** | 아래 참고 |

### SIGKILL: Eureka는 죽은 인스턴스를 3.5~4분간 UP으로 둔다

크래시한 프로세스는 등록을 해제하지 못하므로 Eureka는 lease 만료(90초)와 eviction 주기(60초), 응답 캐시(30초)를 거쳐서야 인스턴스를 뺍니다. 그동안 Gateway는 죽은 인스턴스로 요청을 보내 **`svc-a` 요청의 사실상 전부가 502**였지만 `gateway_upstream_healthy_instances`는 계속 1이었습니다. 그래서 UP 인스턴스 수만 보는 알림은 이 구간에 울리지 않습니다.

| 알림 | SIGKILL 후 첫 firing |
|---|---|
| `GatewayUpstream502Rate` (앱별 502 비율, 우리가 추가) | 46 초 (44 / 46 / 48, 3/3회) |
| `GatewayNoHealthyInstances` (UP = 0) | 263 초 (246 / 263 / 283, 3/3회) |

502 비율 알림이 약 3분 37초 먼저 울렸습니다. 다만 **알림 시각은 성능 수치가 아니라 설정값(폴 10초 + scrape 5초 + `for` 30초)이 정하는 값**이므로 "설계대로 감지됨"의 확인으로만 해석합니다. 핵심 수치는 "UP이 1 이상인데 502가 흐른 시간 ≈ 224초"입니다.

### 호스트 소실: 요청이 타임아웃 없이 매달린다 (새로 발견)

컨테이너 전체를 죽여 IP가 사라지면 연결이 거부되지 않고 응답이 오지 않습니다. 프록시에 업스트림 연결/응답 타임아웃이 없어서 죽은 IP로 간 요청이 **클라이언트 타임아웃(k6 60초)까지 매달렸습니다**:

- k6 p99 / 최대 지연 = 60,001 / 60,024 ms, 클라이언트 타임아웃(status 0) 1,099~1,355건
- 매달린 요청이 k6의 동시성을 채워 **3만 6천~4만 4천 건의 iteration이 누락**(dropped)됨
- Gateway 자체 메트릭에는 클라이언트가 포기한 요청이 `499` 3,663건, 평균 소요 **60.0초**로 기록됨 → 대시보드만 봐도 타임아웃 부재가 드러남

프로세스 크래시(SIGKILL)는 포트가 즉시 거부돼 502가 빨리 떨어지지만, 서버가 통째로 죽으면 훨씬 나쁩니다. 후속 개선(프록시 연결/응답 타임아웃, 연결 실패 인스턴스 일시 제외)의 근거입니다.

## 3. 측정 과정에서 바로잡은 것

- 첫 장애 측정은 폐기했습니다. 백엔드가 `ipAddr`에 호스네임을 등록해서, 컨테이너가 사라지면 Gateway의 DNS 조회가 느리게 실패하고(2.2초) 초당 200건이 libuv 스레드풀을 점유해 Eureka 조회·heartbeat까지 막았습니다 (같은 컨테이너에서 재현: 죽은 이름 200건이 밀린 동안 정상 이름 조회가 22.9초). Gateway 결함이 아니라 하네스 인공물이어서 IP 등록으로 고치고 재측정했습니다.
- `GatewayHigh5xxRate`(5분 윈도우)는 앞 시나리오의 5xx가 이어져 kill 전에 이미 firing인 경우가 많아서, 장애 시작 시 이미 firing인 알림은 결과에서 제외하도록 고쳤습니다. 그래서 위 표에는 이 알림이 없습니다.
- 히스토그램 버킷이 25 → 50 → 100ms로 거칠어서 Prometheus 분위수가 ~48ms로 뭉개졌습니다. 25~100ms 구간을 촘촘하게 바꿨고, 위 지연 표는 버킷과 무관한 k6 값입니다.

## 한계

- 장애 시나리오는 Node 22에서만 재었습니다. 지연은 Node 26으로 다시 쟀지만 두 측정 사이 호스트 상태 차이는 통제하지 못했습니다.
- 단일 서버에서 코어를 나눴지만 같은 호스트의 다른 영향을 완전히 배제하지는 못합니다. p95 이상치가 그 영향일 수 있습니다.
- 백엔드는 합성 지연의 스텁이고 응답이 작습니다. 실제 서비스의 응답 크기·DB 지연은 반영되지 않았습니다.
- Eureka 이미지가 오래되었습니다 (2018년 빌드). 기본값은 현재 Eureka와 같지만 동작이 완전히 같다고 보장하지 않습니다.
- Eureka 조회 비용은 이 구성에서 작습니다 (p50 0.8ms). 같은 호스트의 Eureka라서이고, 원격 Eureka에서는 더 클 수 있습니다. 조회 캐시 도입의 근거로 쓰려면 별도 측정이 필요합니다.
